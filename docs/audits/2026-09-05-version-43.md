# Version 43 audit — 2026-09-05

Historical report. See [the current audit](../AUDIT.md) for the combined release.

## Product goals

Stillpoint Frontier is a browser exploration and survey game. The player travels,
collects materials, records discoveries, completes contracts, crafts equipment,
and places camps. It uses a fixed 96 × 96 km world. The goal is a continuous world
with limited resident simulation and low animation cost.

Three.js is the game engine. React presents the controls and snapshots. Vinext
serves the page through a Cloudflare Worker. Survey state stays in one local
browser slot. There is no active game database or multiplayer server. Optional
auth and database examples are scaffolding, not the source of game state.

Keep the world seed, resource IDs, save compatibility, and survey/dev separation
stable. Preserve the existing visual style and game content.

## Scope and baseline

This pass began at public version 42 and source `58badf2`. It reviewed the project
instructions, entry page and metadata, runtime lifecycle, system order, input,
interaction selection, inventory and crafting, saves and preferences, navigation,
map controls, world height rules, render ownership, build scripts, and test gates.
The baseline type, lint, and coverage checks passed. The baseline had 449 tests;
this pass adds 18 tests.

The [previous audit](2026-09-05-version-41.md) is retained. Its fixes are
part of this baseline. This report covers new findings and remaining limits.

Another task began to edit the original checkout during this review. This pass
uses a separate working copy. Changes from that task are excluded.

## Fixed findings

| Priority | Finding | Change and evidence |
| --- | --- | --- |
| High | Saves rejected valid player and camp heights in Sunscar Canyon. The old lower bound was −100 m; a dry test point is −640.57 m. A deployed item could be consumed without retaining its placement. | Player and placement validation now share a −1,000 to 5,000 m height range. A save round trip retains the player and bedroll at the dry canyon point. Invalid and non-finite heights remain rejected. |
| Medium | Craft controls offered fabrication when the output stack was full. The result reported missing materials even when the ingredients were present. | One pure availability function now drives the controls and transaction. Full stacks show a specific message. Tests cover all six recipes at capacity and with exactly enough room. Failed attempts leave inventory intact. |
| Medium | Horizon changes and Reset Settings also called the survey save path. This could create or replace survey state from title-screen settings. | Both actions write preferences only. Engine tests verify this before and after a survey starts. |
| Medium | The operations tabs lacked a tab-list role, panel labels, and arrow-key control. | The active tab is the single tab stop. Left/Right, Home, and End select and focus tabs. The panel has an active-tab label. Markup tests check the role links and focus attributes. |
| Low | Non-resource candidates ran terrain and collider visibility checks before their score was compared with the best visible target. | Score checks now run first. A 20-candidate fixture uses one visibility query instead of 20. A blocked-best fixture still selects the next visible target. The fixed priority list is also reused. |

The tab behavior follows the [W3C tabs pattern](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/).
The query counts are deterministic test results. They are not measured frame-rate gains.

## Refactors and compatibility

- `world/heightBounds.ts` owns the common saved-height contract.
- `gameplay/crafting.ts` owns availability and atomic crafting rules.
- `Engine` keeps orchestration. It no longer saves a survey from display settings.
- Interaction scoring and line-of-sight rules keep the same target selection.
- The save envelope remains version 8. Versions 1–8 still load. No schema
  migration, dependency update, terrain recipe, or simulation ring change is needed.
- A player or placement already removed by an older save cannot be reconstructed
  from that save. The fix prevents subsequent loss at valid canyon heights.

## Verification

Typecheck and lint passed. All 467 tests in 89 files passed with the existing
coverage thresholds. Measured coverage for the configured include list is
94.32% statements, 86.04% branches, 96.01% functions, and 96.43% lines. These
figures do not describe the entire repository.

The production build passed. The rendered-Worker check passed and returned the
expected title, description, and game shell. It does not use a browser or prove
GPU behavior. The largest client chunk is 1,100,451 bytes (289,754 bytes with
gzip). The build reports the existing large-chunk warning. No load-time gain
is claimed from this pass.

New regression checks live in `canyon-persistence`, `engine-preferences-isolation`,
`operations-panel`, `crafting`, and `interaction-system` under `tests/unit`.
The coverage list now includes the shared height validator and interaction system.

## Remaining limits

- Browser rendering, pointer lock, keyboard focus movement, and real GPU timing
  require separate browser acceptance. They were not tested in this pass.
- The public URL could not be fetched by the available web reader. Site identity
  and public access were checked through Sites; production visual behavior was
  not inspected.
- Survey storage has one browser-local slot and no cross-tab conflict handling.
- Save caps remain 10,000 resource changes, 256 door states, 128 discoveries,
  512 containers, and 64 placements. Large histories can be truncated.
- Chunk construction is synchronous. High-speed travel can cause CPU spikes.
- `Engine.ts` remains large. Session and save orchestration are the next useful
  extraction targets, with tests around launch, load, and disposal.
- Constructor failures and device-specific GPU resource behavior need fault
  injection and hardware checks beyond the existing non-GPU coverage.
- Dependency vulnerability scanning and penetration testing were not performed.
